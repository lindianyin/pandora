## 1. 文档说明

### 1.1 目的

本文档定义棋牌游戏服务端（以下简称「本系统」）的功能需求、非功能需求、接口约束与验收标准，作为设计、开发、测试与验收的依据。

### 1.2 范围

本系统覆盖：账号与登录、大厅、房间与牌桌、对局逻辑、结算与账变、**背包与道具**、匹配、**活动**、好友/社交基础能力、**简单版网页游戏客户端**、**运营后台**、运营配置、监控与运维支撑。  
**不包含**：原生 App/PC 客户端精美 UI、支付宝客户端 SDK 源码本身（服务端对接即可）、内容审核人工审核台（可对接外部系统）。  
**包含**：
- **简单版网页游戏客户端（Vue）**：用于联调与演示完整玩家链路（登录→匹配→斗地主→结算/活动/背包）。  
- **运营后台 Web（Vue）**：通过 HTTPS 调用 Admin API。  
**架构约束**：游戏服务端采用 **单体架构**——业务以单一可执行程序部署；网关/大厅/匹配/对局/钱包/**背包**/活动/Admin API 等为进程内逻辑模块。网页客户端与运营后台为独立前端工程。  
**容量**：单机房 **单实例** 游戏服目标支撑 **CCU 2 万**（不做同构多实例粘滞）。

### 1.3 术语

| 术语 | 说明 |
|------|------|
| 大厅 | 玩家登录后的匹配/选房入口（单体进程内模块） |
| 房间/牌桌 | 一局或多局对战的逻辑容器 |
| 接入层 | 单体进程内的协议接入：TLS、鉴权、限流、路由到业务模块 |
| 对局模块 | 承载具体玩法状态机与出牌校验 |
| 账变 | 金币/钻石等货币的增减流水记录 |
| 幂等 | 同一业务请求重复提交只产生一次有效结果 |
| 活动模块 | 运营活动配置、进度统计、任务/签到/礼包领取与发奖 |
| 道具 | 可发放至玩家背包的虚拟物品；分数量 / 数量+时效 / 时效三类（见 FR-BAG） |
| 背包 | 玩家持有的道具集合；发放、消耗、过期统一由背包模块处理 |
| Protobuf | Google Protocol Buffers，前后端游戏内消息的统一序列化格式 |
| 运营后台 | 面向运营/客服/管理员的 Web 管理端，通过 HTTPS 调用游戏服 Admin API |
| 进程内事件 | 单体进程内的同步回调或异步任务队列，用于模块间通知（非外部 MQ） |

### 1.4 假设与约束

- 开发与发布环境以 **Windows + MSVC** 为主（建议 VS 2022 / MSVC v143，C++17 及以上）。
- 生产可部署于 Windows Server；若后续跨平台，以可移植网络与存储抽象为前提，本期不强制。
- **采用单体架构**：一个主进程承载全部业务模块；同步调用优先进程内接口，禁止为模块拆分而引入服务间 RPC；**远期无微服务拆分计划**。
- **单机房部署**，不需要多区域/多机房。
- 匹配与对局逻辑 **全部自研**，不对接外部中台。
- 存储分工明确：热数据/会话 → Redis；业务、报表、财务与审计 → MySQL。**不使用 Kafka / 外部消息队列**；异步任务用进程内线程池/任务队列。
- 货币体系：**金币 + 钻石**（无房卡）；**道具入背包**，与货币分流。
- 客户端：本期交付 **简单版网页客户端**；协议需兼容后续原生客户端（同一 Protobuf 契约）。
- 对外长连接：**TCP 强制 TLS**；网页客户端使用 **WSS**；HTTP/WS 对外使用 HTTPS/WSS。
- **前后端游戏内消息统一使用 Protobuf**（WSS/TCP 业务包）；`.proto` 为唯一契约源，服务端与网页客户端由同一套定义生成。

## 2. 系统概述

### 2.1 产品目标

提供高并发棋牌类游戏服务端（单体）。首发玩法为 **斗地主（经典 · 简单规则）**；匹配与对局自研；保证对局公平性、数据一致性与资金安全。目标同时在线 **CCU ≥ 2 万**（单机房）。

### 2.2 系统上下文

```
[网页游戏客户端 Vue]              [运营后台 Vue]
      │                               │
      │ HTTPS + WSS                   │ HTTPS（内网优先）
      │ Protobuf 游戏内消息            │ JSON/REST Admin API
      ▼                               ▼
┌──────────────────────────────────────────────┐
│           棋牌服务端（单体进程）                │
│  ┌────────────────────────────────────────┐  │
│  │ 接入层：TLS / 鉴权 / 限流 / 协议适配     │  │
│  └────────────────────────────────────────┘  │
│  ┌──────┬──────┬──────┬──────┬──────┬──────┬─────┐  │
│  │大厅  │匹配  │对局  │钱包  │背包  │活动  │社交 │  │
│  │模块  │模块  │模块  │结算  │道具  │模块  │邮件 │  │
│  └──────┴──────┴──────┴──────┴──────┴──────┴─────┘  │
│  ┌────────────────────────────────────────┐  │
│  │ Admin API / 配置热更 / 异步 Worker 线程池 │  │
│  └────────────────────────────────────────┘  │
└───────────────────┬──────────────────────────┘
                    │
              ┌─────┴─────┐
              ▼           ▼
            Redis       MySQL
         (会话/锁/排行) (业务/报表)
```

### 2.3 核心业务能力

1. 账号注册/登录/会话维持  
2. 大厅浏览、房间创建/加入/旁观  
3. 自动匹配与好友约战  
4. **斗地主（经典）**对局驱动、断线重连、托管  
5. 结算、金币/钻石账变、战绩查询  
6. **背包与道具**：道具配置、发放/消耗/过期；相关模块（活动/邮件/GM/充值赠送等）均可发道具  
7. **活动模块**（首发必上）：签到、任务、礼包；进度 **实时**；奖励可含金币/钻石/**道具**  
8. **运营后台**：玩家/对局/账变/背包查询、活动与道具配置、公告、封禁补发、维护开关等  
9. 运营配置热更新（玩法开关、房间底分、活动/道具开关等）  
10. 风控基础能力（频率限制、异常对局检测钩子）  
11. **简单版网页游戏客户端**：登录、大厅、匹配、斗地主对局、结算展示、基础活动、**背包**

## 3. 功能需求

### 3.1 接入与协议层（FR-GW）

| ID | 需求描述 | 优先级 |
|----|----------|--------|
| FR-GW-01 | 支持 **HTTP/HTTPS**：用于登录、支付回调、运营拉取、健康检查等短连接接口 | P0 |
| FR-GW-02 | 支持 **WS/WSS**：用于大厅推送、房间状态、对局实时消息 | P0 |
| FR-GW-03 | 支持 **TCP + TLS（强制）**：生产与对外环境禁止明文 TCP；用于低延迟长连接（原生客户端优先） | P0 |
| FR-GW-04 | 三种协议共用统一会话鉴权（Token / Session），协议切换不丢登录态 | P0 |
| FR-GW-05 | **游戏内消息（大厅/房间/对局/活动推送等，经 WSS/TCP）统一使用 Protobuf**；禁止游戏内长连接再用 JSON 业务包 | P0 |
| FR-GW-05a | 游戏内帧格式固定为：**长度头 \| msg_id \| 消息体**。长度头与 `msg_id` 均为 **uint32 小端（little-endian）**；长度头表示其后 `msg_id + 消息体` 的字节总长；消息体为对应 Protobuf 序列化字节 | P0 |
| FR-GW-05b | 使用 **proto3**；`.proto` 纳入版本管理；服务端（C++）与客户端由同一契约生成代码；破坏性变更升主版本号/`msg_id` 段 | P0 |
| FR-GW-05c | HTTPS 短连接（登录、支付回调、健康检查、部分查询）可采用 JSON/REST；与游戏内 Protobuf 通道并存，鉴权体系统一 | P0 |
| FR-GW-06 | 心跳检测：超时踢下线并触发托管/断线逻辑（心跳亦为 Protobuf 消息） | P0 |
| FR-GW-07 | 连接限流、IP/账号频控、恶意包检测与断连 | P0 |
| FR-GW-08 | HTTPS/WSS/TCP-TLS 证书可配置热加载（不强制中断全部连接，允许滚动） | P1 |

### 3.7 背包与道具（FR-BAG）

进程内 **背包模块** 为道具发放/消耗/查询的唯一权威入口；活动、邮件、GM、充值赠送、对局奖励等均不得绕过该模块直接改持有量。

#### 3.7.1 道具类型

| 类型码 | 名称 | 语义 | 持有形态 |
|--------|------|------|----------|
| `qty` | **数量道具** | 仅计数，不过期 | 同 `item_id` 可堆叠为一行，`quantity` 增减 |
| `qty_ttl` | **数量+时效道具** | 既有数量，又有过期时间 | 同 `item_id` 且同 `expire_at` 可堆叠；过期后不可用 |
| `ttl` | **时效道具** | 仅过期时间，有效期内持续生效（类似 buff）；同 `item_id` 只保留一行；再次获得时过期时间在现有有效期上**累加** | 到期失效 |

#### 3.7.2 功能需求

| ID | 需求描述 | 优先级 |
|----|----------|--------|
| FR-BAG-01 | 进程内 **背包模块**：道具定义加载、玩家背包查询、发放、消耗、过期处理；写路径幂等；异常不得拖垮对局主循环 | P0 |
| FR-BAG-02 | **道具定义**可配置并热更：`item_id`、名称、图标、类型（`qty`/`qty_ttl`/`ttl`）、是否可堆叠、默认时效（秒，仅时效类）、业务标签（如 `avatar_frame`/`ticket`）、上下架 | P0 |
| FR-BAG-03 | 玩家可查询背包列表（过滤已过期/已耗尽可配）；展示数量、过期时间（可读时间）、道具元信息 | P0 |
| FR-BAG-04 | **发放（Grant）**：统一接口 `Grant(uid, item_id, quantity, expire_policy, idempotent_key, biz_type, ref_id)`；写持有记录 + 道具流水；重复幂等键不重复加 | P0 |
| FR-BAG-05 | **消耗（Consume）**：校验类型、数量、未过期；原子扣减；不足则失败；写流水 | P0 |
| FR-BAG-06 | **数量道具（qty）**：仅维护 `quantity`；`expire_at` 使用哨兵「不过期」；堆叠规则为同 `item_id` 合并 | P0 |
| FR-BAG-07 | **时效道具（ttl）**：发放时按默认时长或显式时长计算到期；有效期内持续可用（buff）；再次获得同 `item_id` 时过期时间累加（从 `max(现在, 当前expire)` 起加时长）；同 `item_id` 仅一行；到期后不可用 | P0 |
| FR-BAG-08 | **数量+时效道具（qty_ttl）**：同时维护 `quantity` 与 `expire_at`；同 `item_id`+同到期时刻可堆叠；过期后剩余数量作废 | P0 |
| FR-BAG-09 | 过期处理：**惰性过期**（查询/消耗时判定）为主；可选定时清理任务归档过期行（异步线程池） | P0 |
| FR-BAG-10 | 道具流水 `item_ledger`：记录增减、余额后数量、到期时刻、业务类型、幂等键、关联单号；不可篡改历史 | P0 |
| FR-BAG-11 | **相关模块必须支持道具**（奖励/附件/补发字段可引用 `item_id`）：活动领奖、系统邮件附件、GM/Admin 补发、充值档位赠送（P1）、对局/任务额外掉落（P1，可先配置打通） | P0 |
| FR-BAG-12 | 奖励描述统一结构（示意）：可同时含 `currency`（金币/钻石）与 `items:[{item_id,quantity,expire_sec?}]`；货币走钱包，道具走背包 | P0 |
| FR-BAG-13 | 管理端：道具定义 CRUD/上下架；按 UID 查看背包与流水；人工发放/回收道具（二次确认 + 审计） | P0 |
| FR-BAG-14 | 客户端推送：背包变更可推送 Protobuf 通知（如 `BagUpdate`），至少在发放成功后可选推送或由客户端主动刷新 | P1 |
| FR-BAG-15 | 首发不要求玩家间交易/寄售；道具不可转赠（除非后续单独开需求） | P0 |

## 4. 数据存储需求

### 4.1 分工

| 组件 | 用途 | 典型数据 |
|------|------|----------|
| **Redis** | 热数据、会话、分布式锁、匹配队列、在线状态、排行榜、限流计数、**活动进度缓存** | `session:{uid}`、`room:{id}`、`match:queue:{game}`、`rank:day`、`act:prog:{aid}:{uid}` |
| **MySQL** | 业务主库、强一致事务；报表/财务对账/审计归档；**活动配置与领取记录**；**道具定义与背包/流水** | 账号、角色、房间配置、对局摘要、账变、好友、邮件、活动定义、任务进度、领奖流水、道具定义、背包持有、道具流水、GM 审计、运营审计 |

### 4.2 数据原则

| ID | 需求 | 优先级 |
|----|------|--------|
| DR-01 | MySQL 账变与余额更新必须同事务；失败可回滚；**道具发放/消耗与道具流水同事务** | P0 |
| DR-02 | Redis 与 MySQL 以 MySQL 为准；Redis 可重建 | P0 |
| DR-03 | 关键写操作具备幂等键与唯一约束 | P0 |
| DR-04 | 敏感数据加密或脱敏；日志禁止输出完整 Token/密码 | P0 |
| DR-05 | **不上 MySQL 读写分离**；单主库（可保留备份/主备容灾）；历史数据可按策略归档分表 | P0 |
| DR-06 | Redis/MySQL 连接池化；超时、重试、熔断可配 | P0 |

### 4.3 核心实体（逻辑模型）

- `user`：账号基础信息  
- `player_profile`：昵称、头像、**金币、钻石**、等级  
- `session`：登录会话（Redis 为主）  
- `game_define` / `room_template`：玩法与场次配置  
- `room` / `seat`：运行时房间（Redis + 必要落库）  
- `game_round`：对局局号、参与者、起止时间、结果摘要  
- `ledger`：账变流水  
- `replay`：操作序列或录像索引  
- `ban` / `gm_audit`：封禁与 GM 审计  
- `admin_user` / `admin_role`：运营后台账号与角色权限  
- `admin_audit`：管理员操作审计  
- `activity_define`：活动元数据、时间窗、规则与奖励配置  
- `activity_progress`：玩家活动进度  
- `activity_claim`：领奖/发奖流水（幂等键）
- `pay_product`：充值档位配置（金额、钻石、赠送、状态；可含赠送道具）
- `pay_order`：支付订单（支付宝交易号、状态、到账结果）
- `item_define`：道具元数据（类型 `qty`/`qty_ttl`/`ttl`、默认时效、堆叠、上下架）
- `bag_item`：玩家背包持有（uid、item_id、quantity、expire_at）
- `item_ledger`：道具增减流水（幂等键、业务类型、关联单号）

## 6. 技术约束与架构要求

### 6.1 架构原则（单体）

| 原则 | 说明 |
|------|------|
| 单进程部署 | 对外提供一个主可执行文件；HTTP(S)/WS(WSS)/TCP、业务、Admin、异步 Worker 均在同一进程（线程池） |
| 逻辑分模块 | 模块间同步调用走进程内 API；跨模块禁止隐藏的网络调用 |
| 异步不拆服 | 邮件、归档、统计等用线程池，不引入外部 MQ、不拆微服务 |
| 状态集中 | 牌桌运行时状态在本进程内存；持久化依赖 Redis/MySQL；**单实例承载全部在线** |

### 6.2 开发约束

- 语言：**C++17+**，编译器：**MSVC**（Windows）；**运营后台与网页游戏客户端均为 Vue**。
- 逻辑模块：`net`（接入）/ `lobby` / `match` / `game` / `wallet` / `bag`（背包道具）/ `activity` / `social` / `admin` / `common` / `proto`（生成代码与编解码）。
- 网络库、**Protobuf（proto3）**、ORM/DB 访问层需统一封装；帧编解码严格遵循：`uint32 LE 长度头 | uint32 LE msg_id | Protobuf 消息体`。
- 第三方库选型需可商用（许可证审计）。

### 6.3 部署形态

| 形态 | 说明 |
|------|------|
| 标准部署 | **单机房单实例**游戏服 + Redis + MySQL；**game-web（Vue）** 与 **admin-web（Vue）** 静态资源由 Nginx 托管；**域名与证书由运维提供** |
| 高可用 | 游戏服可用主备冷备切换；**不以多实例粘滞扩展 CCU** |
| 禁止 | 游戏业务不拆微服务；不部署 Kafka；运营后台不得直连玩家长连接通道 |

### 6.4 配置

- 统一配置文件（JSON/YAML/TOML + 环境覆盖）。
- 必须可配：监听端口、证书路径、Redis/MySQL 连接串、工作线程数、日志级别、各玩法/活动开关、**支付宝商户/沙箱·正式参数**、钻石兑换汇率默认值。

### 7.2 WS/TCP 游戏内消息（Protobuf）

**帧布局（已确认）**

```text
+------------------+------------------+------------------+
| 长度头            | msg_id           | 消息体            |
| uint32 小端       | uint32 小端       | Protobuf bytes   |
| (= len(msg_id)+len(body)) |                  |                  |
+------------------+------------------+------------------+
```

长连接业务包统一为 Protobuf（proto3）。示意 `msg_id`（具体以 `.proto` 为准）：

| 方向 | MsgId / Message | 说明 |
|------|-----------------|------|
| C→S | `Heartbeat` | 心跳 |
| C→S | `JoinRoom` / `LeaveRoom` | 进出房 |
| C→S | `Ready` / `GameAction` | 准备/出牌操作 |
| S→C | `RoomState` | 房间快照 |
| S→C | `GameEvent` | 对局事件流 |
| S→C | `Settle` | 结算结果 |
| S→C | `ActivityUpdate` | 活动进度/可领奖励变更 |
| S→C | `BagUpdate` | 背包变更通知（发放/消耗/过期） |
| S→C | `Kick` / `Maintain` | 踢下线/维护 |

> 字段级定义以仓库内 `.proto` 及《通信协议设计文档》为准；本文仅列消息类别。

## 8. 关键业务流程

### 8.1 登录进房对局

1. 客户端 HTTPS 登录 → 获 Token  
2. 持 Token 建立 WSS/TCP → 接入层校验会话  
3. 选择场次 → 匹配成功 → 分配房间（进程内对局模块）  
4. 全员准备 → 开局 → 行牌 → 结算账变 → 续局或散桌  

### 8.2 断线重连

1. 连接断开 → 进入托管（可配延迟）  
2. 客户端重连并鉴权 → 拉取房间快照  
3. 恢复操作权或继续托管直到玩家主动接管  

### 8.3 结算一致性

1. 对局模块生成结算单（含 round_id）  
2. 钱包模块以 round_id 幂等入账（MySQL 事务，进程内调用）  
3. 成功后广播 `SETTLE`；进程内通知活动模块更新进度；归档/统计可丢线程池异步执行  
4. 入账失败则重试/告警/安全散桌策略；禁止重复加币  

### 8.4 活动进度与领奖

1. 对局结算 / 登录等在进程内触发活动进度更新（**实时**）  
2. 活动模块更新进度（幂等）→ 立即推送 `ActivityUpdate`（可领则提示）  
3. 玩家请求领奖 → 校验时间窗/进度/库存 → 进程内调用钱包发货币 / **背包发道具** → 记 `activity_claim`  
4. 活动模块异常时对局/匹配不受影响  

### 8.5 道具发放与消耗

1. 业务模块（活动/邮件领取/GM/充值到账）组装奖励 → 调用背包 `Grant`（带幂等键）  
2. 背包按道具类型更新 `bag_item`（qty 堆叠 / qty_ttl 按到期堆叠 / ttl 写到期）并写 `item_ledger`  
3. 可选推送 `BagUpdate`；客户端刷新背包页  
4. 消耗：`Consume` 校验未过期与数量 → 原子扣减 → 流水；不足则失败  
5. 查询时惰性标记/过滤过期项；异步任务可归档过期行  

### 8.6 进程内事件流（示例）

```
对局结算 ──同步──▶ 钱包入账 ──同步──▶ 活动进度 ──推送──▶ 客户端
                 └─异步线程池──▶ 归档 / 统计
登录成功 ──同步──▶ 活动(签到) / 会话
活动/邮件领奖 ──同步──▶ 钱包(货币) + 背包(道具) ──推送──▶ BagUpdate
运营改配 ──Admin──▶ 配置热更 ──广播──▶ 在线玩家
```

## 10. 测试与验收

### 10.1 测试类型

- 单元测试：玩法校验、账变幂等、状态机迁移、**活动领奖幂等/库存扣减**、**道具发放/消耗/过期幂等**

- 压力测试：连接、匹配、出牌广播、DB 瓶颈、活动领奖洪峰  
- 混沌测试：杀主进程、Redis 闪断、重复结算、活动/背包模块故意抛错隔离  
- 安全测试：越权、重放、篡改牌面包、**伪造领奖/伪造消耗道具**  

### 10.2 验收标准（P0 必须）

1. 三种协议均可完成登录与进房（HTTPS 登录 + WSS/TCP+TLS 对局）；**游戏内包可被 Protobuf 正确编解码**。  
2. 任意合法操作均服务端校验；篡改包无效。  
3. 重复结算请求不产生双倍发放；**活动重复领奖不产生双倍发放**；**道具重复发放幂等键不产生双倍持有**。  
4. 断线重连后牌面信息正确且不泄露隐藏牌。  
5. MySQL 账变与余额一致；道具持有与 `item_ledger` 一致；Redis 丢数据后可从 DB 恢复会话外业务数据。  
6. 维护模式与封号即时生效。  
7. 核心指标与错误日志可观测。  
8. **以单体单进程完成全链路**；活动/背包模块异常不影响对局；首发活动（签到/任务/礼包）可配置、**实时进度**、可领奖（含道具）。  
9. 不存在大厅/对局/活动等独立微服务进程依赖；**不依赖 Kafka**（中间件仅 Redis/MySQL）。  
10. 压测达到 **CCU 2 万**（**单实例**）；TCP 明文连接在生产配置下被拒绝。  
11. 首发仅 **斗地主经典简单规则**；货币仅 **金币+钻石**；道具三类（数量 / 数量+时效 / 时效）可配置与发放。  
12. **运营后台（Vue）**可完成：登录鉴权、玩家查询/封禁、账变补发、场次配置、活动配置（含上下架）、**道具定义与背包补发**、公告/邮件（附件可含道具）、维护开关、充值档位（含上下架）；列表页具备分页与查找；时间字段为可读格式；关键操作有审计（无双人审批）。  
13. 游戏内包帧为 `uint32 LE 长度头 | uint32 LE msg_id | 消息体`；支付为支付宝 **APP 支付**（参数可配）。  
14. **简单版网页客户端**能完成：登录→匹配→斗地主一局→结算；至少三开窗口联调；活动领奖与**背包页**可演示。  
15. 活动、邮件、GM 补发等路径发放道具均经背包模块；过期道具不可消耗。
